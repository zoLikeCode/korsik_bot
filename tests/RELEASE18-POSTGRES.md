## Что фактически проверено новым набором

| Проверка | Фактический результат |
| --- | --- |
| Подписанный синтетический launch и роли | Сервер вернул существующую MANAGER роль/scope, проигнорировав предложенное HR_ADMIN в подписанном User JSON. Cookie-сессия доступна через реальный `/auth/session`; отозванный binding делает её недоступной. |
| Replay и реальные ограничения PostgreSQL | Повтор в том же браузере сохраняет сессию, другой браузер получает 409. При двух конкурентных HTTP-запросах с одним launch: `[200,409]`, одна сохранённая сессия/metadata. String(36) для metadata IDs проверен реальной схемой PostgreSQL. |
| Сотрудник | Синтетическая заранее подтверждённая server binding разрешила provision только EMPLOYEE существующей карточки; смена episode лишила старую сессию доступа. При current HR-owned pointer существующая enabled EMPLOYEE входит при наличии disabled historical User; неверный pointer даёт 403 без обходного provision. Это fixture предусловия HR-подтверждения, не живое подтверждение личности в MAX. |
| Анкета/версия/расписание | Реальные HTTP 428 без ETag, 412 при устаревшем ETag, 409 при изменении опубликованной версии или несовпадении preview. Согласование/публикация → закреплённая аудитория → два tick → один job → настоящий business worker claim/handler/commit → один survey_run. |
| Receipt и напоминания | Синтетический trusted receipt вызывает реальный opening hook; повтор hook не дублирует два настроенных reminder jobs. MAX send не производился. |
| Ответы и доступ | Сотрудник через настоящие HTTP endpoints сохранил шкалу и текст, затем завершил опрос. Raw ответы доступны scoped HR; HEAD для группы из одного человека получает suppressed aggregate и 403 на raw endpoint. Отзыв scope автора даёт 404 при повторном чтении прежних raw ответов. |
| Отмена/изоляция | Отмена отдельной будущей кампании закрывает её enrollment, не меняя завершённую анкету. Тексты добровольного опроса не создают general feedback/sentiment jobs. |

## Изоляция и очистка

Wrapper каждый раз отказывался перезаписывать существующую `korsik_integration_check`, создавал её отдельно и восстанавливал **только schema-only pg_dump**. Скрипт нового набора дополнительно отказывался работать с не-PostgreSQL, другой БД или непустыми domain/users/sessions перед seed. Фикстуры содержат только синтетические карточки и локальный исходный seed приложения.

Новый helper не монтировал рабочие blobs/models и реальный MAX token. Подпись использовала публичный тестовый ключ из исходника; `read_secret` MiniApp в этом процессе разрешал только этот фиктивный путь. Внешний HTTP transport блокировался; попыток внешнего HTTP — **0**, отправок MAX и обращений к модели — **0**. SessionLocal/middleware DB dependency перенаправлялись только внутри одноразового процесса на изолированную БД; production-процессы не менялись.

Оба EXIT cleanup завершились успешно. Новый cleanup дополнительно запросил `pg_database` после `dropdb --force`: осталось **0** изолированных БД. Исторические `postgres-check-report.json` и source15 отчёты не заменены. Root/оператору передан сигнал освобождения окна.

Границы: доказательства не означают приёмку компанией, внешний security audit, проверку настоящего MAX owner account, перезагрузку VM или гарантированное восстановление при отказе провайдера. Удаление временной БД не является проверкой восстановимости production backup.
