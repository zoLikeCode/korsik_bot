# Обновление приложения: MAX MiniApp, опросы и поддержка

Этот документ описывает **текущие исходники**, а не утверждает, что обновление уже развёрнуто на стенде. Состояние реального HTTPS-адреса, установки systemd, запуска из MAX и перезагрузки VM оператор фиксирует отдельно после выполнения проверок ниже. Секретов, действительных приглашений и персональных переписок здесь нет.

Проверенный локальный прогон перед экспортом контракта: **447 тестов и 18 subtests PASS, 28,77 с**; Ruff `backend tests --select F,E9` — PASS. Единственное предупреждение — upstream Starlette/AnyIO deprecation. Это инженерные проверки; приёмка компанией не проводилась. Более ранние измерения source15 в `ARCHITECTURE.md`, `OPERATIONS.md`, README и JSON-отчётах сохраняют свои прежние образы и границы.

## 1. Роли и запуск через MAX

Используется одно React-приложение с серверными ролями. Обычный браузер сохраняет вход по email/паролю. В MAX frontend получает исходный `WebAppData`/`WebApp.initData`, передаёт строку в `POST /api/v1/auth/max-miniapp` и проверяет, что защищённая cookie действительно принята webview через `/api/v1/auth/session`.

Backend проверяет HMAC-SHA256 с производным ключом `WebAppData`, уникальность/однозначность полей, подпись, `auth_date` и `query_id`. Срок launch — до 3600 секунд, допустимое будущее смещение — до 30 секунд. `query_id` сохраняется как replay fence; повтор допустим только для того же запуска в уже выданной действующей сессии с правильной CSRF cookie. Сырые launch-данные не сохраняются и не становятся источником роли, scope, имени или назначения сотрудника.

Личность разрешается только через действующую серверную привязку:

- HR/руководитель — подтверждённая собственная `principal_binding`, включённый существующий User и разрешённая роль.
- Сотрудник — уже подтверждённая HR `max_binding`, актуальная карточка и текущий период найма. Если после такого подтверждения веб-аккаунта ещё нет, сервер создаёт только User роли `EMPLOYEE` для существующей карточки со случайным непредоставляемым паролем. Новый сотрудник, кадровое подтверждение или повышенная роль из launch не создаются.
- Неизвестная, неоднозначная, отозванная или устаревшая привязка даёт отказ. Временная/старая MAX-сессия не обходит смену роли, disabled User, OFFBOARD/REHIRE или отзыв binding: `auth.session_user` проверяет её актуальность на каждом защищённом запросе.

Выдаваемая MAX-сессия ограничена максимум часом; cookies — `Secure`, `SameSite=None`, session cookie — `HttpOnly`, запись защищена CSRF. Наличие кнопки/видимого экрана не заменяет backend RBAC. В настоящий MAX owner account эта реализация автоматически не входит и настройки бота не меняет.

**Настройка владельцем бота и реальный запуск остаются отдельным действием.** Нужны актуальный доверенный HTTPS URL, настройка точки входа MiniApp в управлении ботом и запуск с настоящими подписанными данными MAX. Владение ботом не подтверждается наличием его API token. Локальная проверка синтетических HMAC не доказывает успешную авторизацию на реальном мобильном устройстве.

В MiniApp загружается официальный bridge `https://st.max.ru/js/max-web-app.js`. Это отдельный внешний ресурс канала MAX; генерация, поиск и OCR остаются локальными. Для обычного браузерного входа bridge не загружается. При недоступном SDK используется browser viewport; отсутствие подписанных launch-данных не заменяется доверием к `initDataUnsafe` или данным URL. В полностью отключённой от MAX сети доступен обычный корпоративный веб-вход, а не обещание работы MAX без связи с его инфраструктурой.

## 2. Интерфейс и конструктор программы

| Роль | Основная навигация |
| --- | --- |
| Сотрудник | Диалог, Опросы. |
| Руководитель подразделения | Обзор, Опросы со сводками. |
| HR | Обзор, Сотрудники, Схема, База знаний, Опросы, Диалоги, Аналитика. |
| Руководитель подбора | Обзор, Опросы, Аналитика; Сотрудники только при отдельном `employee_drilldown`. |
| Администратор платформы | Эта продуктовая оболочка не открывает HR-разделы автоматически. Технические API и CLI сохраняют собственные права. |

Отдельные разделы «Обращения» и «Настройки» из основной навигации убраны. Их старые backend API этим не удалены и не становятся общедоступными. Вопросы сотрудников HR обрабатывает из «Диалогов». Не следует давать старый путь React как инструкцию к действию, которого больше нет в текущей оболочке.

Конструктор — **экран «Схема» с графом**, а не пошаговый мастер. Пользователь создаёт/выбирает узлы, перемещает их, соединяет и удаляет связи, редактирует блоки и порядок ветвей. Layout хранится отдельно от исполнения; сохранение, validation, simulation, source-change review, publish и migration по-прежнему серверные операции с версиями и CAS. Локальная API-проверка подтверждает сохранение/перезагрузку графа и отказ при устаревшем ETag, но не заменяет проверку всех жестов на реальном мобильном MAX.

Новые готовые шаблоны дашбордов/аналитики не придуманы: содержательные макеты и показатели, которые пользователь обещал прислать, **ожидаются**. Существующая SQL-аналитика не выдаётся за эти будущие шаблоны.

## 3. Добровольные опросы с расписанием

`survey_campaigns.py` добавляет `survey_template`, `survey_template_version`, `survey_campaign` и `survey_campaign_enrollment`. Ответы сохраняются в существующих `survey_run`, `survey_answer_revision` и typed capture; отдельной неподконтрольной MAX-анкеты нет.

HR без кода задаёт название/пояснение, вопросы шкалы, одного/нескольких вариантов или свободного текста, порядок и благодарность. Все вопросы допускают явный пропуск, весь опрос — отказ. Типизированные входные JSON-модели запрещают неизвестные поля. Ответы проверяет сервер, текст не превращается в число/вариант по догадке LLM.

### Версии и аудитория

Версия проходит `DRAFT → REVIEW_REQUIRED → APPROVED → PUBLISHED`. После выхода из DRAFT редактирование запрещено; отклонение возвращает черновик, опубликованная версия изменяется через новый draft. Публикует HR_ADMIN в своей области. Review, сохранение, публикация и перепланирование требуют причины и актуального ETag там, где предусмотрен CAS. Scope шаблона наследует grant автора либо явно ограничивается им; роль HR не даёт права расширять область.

Кампания закрепляет точную опубликованную версию и аудиторию по площадкам, конкретным сотрудникам, PREBOARDING/ACTIVE, OFFICE/PRODUCTION и роли привязанной учётной записи. Для роли руководителя/HR в рассылке нужна существующая карточка сотрудника; сам список User не становится списком получателей. Выключенные/несогласованные связи аккаунта не включаются в аудиторию.

Перед сохранением HR видит получателей и период. Сервер возвращает `preview_hash`, который закрепляет настройки, версию, scope, карточки и episodes. Изменение аудитории/настроек требует нового preview. После сохранения новые сотрудники не добавляются незаметно; отправка повторно проверяет текущий grant автора и применимость каждого закреплённого получателя.

### Даты и доставка

Форма интерпретирует wall time в выбранной IANA zone. Несуществующее время при DST отклоняется; для повторяющегося времени пользователь явно выбирает смещение. API принимает даты с offset и нормализует их в UTC; IANA zone сохраняется для отображения. Один campaign — один период начала/окончания; повторяющийся календарь серий опросов не заявлен.

Scheduler создаёт durable SQL jobs `DOMAIN_SURVEY_CAMPAIGN_DELIVER` и `DOMAIN_SURVEY_CAMPAIGN_REMINDER`. Уникальные ключи и generation fence не дают старому расписанию создать повторный run. Напоминаний максимум три; заданные часы отсчитываются от **принятой доставки первого вопроса**, а не от enqueue. Срок ответа ограничен окончанием кампании. Отказ, завершение, expiry, изменившийся episode/scope, отмена и недействующая lease не разрешают позднюю отправку или ответ.

Программа адаптации и пользовательские опросы имеют одну активную survey lane на сотрудника: общий row lock и проверка действующего run не позволяют открыть вторую анкету поверх первой. Во время разговора с человеком новый campaign run откладывается durable job. После освобождения lane он может открыться в оставшемся периоде; открытие не обещается ровно в одну секунду при занятом диалоге.

Перепланирование разрешено только до начала при отсутствии открытого run; generation изменяется, старые будущие задания перестают действовать. Начатые/отвеченные опросы не перезаписываются. Отмена закрывает оставшийся ввод/доставку и связанные captures, но сохраняет ответы, answer revisions и черновики в истории.

### Приватность и аналитика

Это **идентифицированный добровольный рабочий опрос**, не анонимная диагностика. Первое сообщение содержит явное пояснение: ответы связаны с карточкой и доступны HR в рамках его текущих полномочий, любой вопрос можно пропустить. Психологические диагнозы, индивидуальные профили, автоматические кадровые решения и медицинская оценка не рассчитываются.

HR читает ответы через отдельный scoped endpoint. MANAGER/HEAD_TALENT получают только агрегаты: минимум пять различных участников группы и минимум пять ответивших на конкретный вопрос. Малые категории/остаточные клетки скрываются; тексты и индивидуальные оценки не возвращаются. Это ограниченная защита малых групп, а не заявление о формальной дифференциальной приватности.

Тексты этих анкет исключены из общей sentiment/feedback analysis. Пользовательские кампании не меняют показатели завершённости и числовые средние базовой адаптации и её digest. Их результаты доступны отдельно в «Опросах». Локальный end-to-end regression проверяет это на реально сохранённых ответах и подтверждённом opening receipt.

## 4. Поддержка без лишней кнопки

Если поиск возвращает `HANDOFF`, сотруднику уходит нейтральное сообщение:

> Вопрос принят. Уточняем информацию; ответ появится здесь.

Worker создаёт/переиспользует открытое case текущего employee/episode/conversation и уведомляет включённого HR с доступом. Если назначенный HR не существует, выключен, имеет другую роль или потерял scope, уведомления идут доступным HR; недействующее назначение не блокирует принятие свободного обращения. Руководителю по одной только роли HR-уведомление не отправляется.

Такое ожидание ответа **сохраняет BOT**: следующий обычный вопрос создаёт новый RAG turn. Автоматический `HANDOFF` не равен ручному переводу всего диалога в `WAITING_HR`; прежний явный API перевода существует отдельно. Повторное завершение того же answer не создаёт второй case, сообщение или уведомление.

Только явный `POST /cases/{id}/claim` допустимым HR переключает текущий диалог в `HUMAN`. Отдельное сообщение «подключился HR» при claim не отправляется. Ответ человека в MAX начинается **«Ответ команды поддержки:»**; в SQL автор сообщения — HR, а не LLM. Presend повторно проверяет текущую привязку, назначение оператора, его роль и scope. При закрытом case старое ожидающее уведомление подавляется. Возврат к BOT остаётся отдельным действием.

При формировании employee callback-кнопок транспорт удаляет legacy `CONTACT_HR`, `HANDOFF`, `CONTACT_RECRUITER`, включая `kind` alias/JSON payload и прежнюю подпись «Связаться с HR». Кнопки поиска и оригинала источника сохраняются. Это изменение UI потока, а не удаление серверного RBAC или скрытый запрет обычного вопроса. Подтверждённый ответ с источником сохраняет свой текст, citations и кнопку оригинала.

## 5. Healthchecks и ограниченный host watchdog

Docker `restart: unless-stopped` помогает при завершении процесса, но сам по себе не перезапускает работающий `unhealthy` контейнер. Для этого подготовлены `scripts/runtime-watchdog.py` и явный операторский installer `scripts/install-runtime-services.sh`.

| Сигнал | Что реально проверяется |
| --- | --- |
| Worker / answer-worker / ingest-worker | Атомарный `/tmp/korsik-heartbeat` после рабочего цикла, включая idle; допустимый возраст соответственно 120/210/720 секунд. |
| Scheduler | Heartbeat рабочего цикла, возраст до 45 секунд. |
| MAX connector `/healthz` | Созданы четыре фоновые задачи и ни одна не завершена/не отменена. Это не проверка доступности MAX или доставки конкретного сообщения. |
| API `/healthz`, `/readyz` | Процесс/версия и отдельная проверка SQL соответственно. |
| Tunnel | Его supervisor проверяет origin, edge readiness и реальный HTTPS до публикации адреса; это не гарантия стабильности Vast/DNS или постоянного домена. |

Базовый FULL whitelist состоит из 14 persistent services: `postgres`, `qdrant`, `api`, `worker`, `answer-worker`, `ingest-worker`, `scheduler`, `encoder`, `reranker`, `generator`, `parser`, `web`, `max-connector`, `tunnel`. Одноразовые `init-data`/`migrate` и другие Compose projects не входят.

Systemd boot unit запускает уже имеющиеся образы через `up -d --no-build --pull never`. Timer проверяет состояние раз в 20 секунд после 40 секунд от boot. Для действия нужны три подряд плохих наблюдения, startup grace 180 секунд или 300 секунд для моделей/parser, cooldown 300 секунд, максимум два действия за проход и два на сервис за час. Бюджет атомарно резервируется до Docker action и переживает падение watchdog. Учитываются incarnation/container ID, свежий inventory и блокировка параллельных запусков; неоднозначные контейнеры, неверное состояние/clock rollback или недоступный Docker не вызывают произвольный restart.

Действие — restart только закреплённого контейнера либо создание отсутствующего выбранного сервиса без dependencies/build/pull. Нет `down`, удаления volumes, `prune`, скачивания образов, перезапуска всего стека или тестового вызова модели. Остановка и восстановление хоста самим провайдером за пределами этого механизма.

Installer нацелен на **базовый FULL deployment**. Для CORE/on-prem с намеренно отключёнными generator/tunnel оператор сначала адаптирует boot Compose arguments и whitelist/override восстановления. Нельзя включать таймер с отсутствующим намеренно выключенным сервисом в списке: он попытается его создать.

Журнал выделен в namespace `korsik-runtime`: persistent cap64M, runtime cap32M, retention7day, rate limit6 записей/минуту. Это отдельные caps от Docker json-file logs (10M ×3 на контейнер).

## 6. Операторские команды и оставшаяся проверка

Следующие команды — инструкция к будущему явному действию оператора, **не протокол уже выполненного reboot/deploy**. Они не содержат секреты и не печатают `.env`.

```sh
# Предварительно проверьте actual Compose/environment и сохраните backup.
# Render-only не устанавливает unit и не обращается к Docker/systemd.
scripts/install-runtime-services.sh --render-only /private/korsik-units-review

# На Linux systemd-хосте, после проверки rendered units и путей:
sudo scripts/install-runtime-services.sh --no-enable
sudo systemctl enable --now korsik-runtime.service korsik-watchdog.timer
systemctl status korsik-runtime.service korsik-watchdog.timer --no-pager
journalctl --namespace=korsik-runtime -u korsik-watchdog.service --since today --no-pager
```

Для планового вмешательства нужен maintenance marker **до** остановки сервиса, иначе watchdog воспримет остановку как отказ:

```sh
sudo touch /opt/korsik/runtime/maintenance
# Выполнить согласованные operator update/restore операции и проверить состояние.
# Для restore также распознаётся /opt/korsik/runtime/restore-in-progress.
sudo rm /opt/korsik/runtime/maintenance
```

Marker следует удалять только после успешной проверки. Если операция прервана, marker сохраняется как видимое состояние обслуживания; это не повод заявлять, что автоматическое восстановление активно. Оператор не должен стирать watchdog-state для обхода restart cap без выяснения причины.
