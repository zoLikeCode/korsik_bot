## Постоянный HTTPS-вход

VPS `212.57.127.220` использует отдельный `korsik-tunnel` и ключ, созданный на этом VPS. На Vast отдельный `korsik-edge` допускает только local forwarding к `127.0.0.1:8080` и только с IPv4 VPS. Закрытые ключи существующего root-доступа не переносились; root effective sshd config сохранился. Реальные проверки запретили shell, другое назначение и reverse forwarding: [ru-ingress-tunnel-report.json](tests/ru-ingress-tunnel-report.json). Это не HA: доступ зависит от VPS, SSH-сети и узла Vast.

Для **app.korsik-demo.ru** настроена A-запись, выпущен production-сертификат Let's Encrypt, проверены CA/SNI, HTTP→HTTPS, ACME route, CSP для MAX и 23 файла приложения. Certbot timer и renewal hook включены, существующие сайты ISPmanager сохранены. [ru-ingress-https-report.json](tests/ru-ingress-https-report.json) отдельно фиксирует неполное распространение DNS на одном authoritative NS и неуспешную повторную проверку свежего внешнего клиента. Сертификат apex `korsik-demo.ru` этим протоколом не подтверждается; канонический адрес использует поддомен `app`.

На Vast изменены только `PUBLIC_URL=https://app.korsik-demo.ru`, `SECURE_COOKIES=true`, `MAX_PUBLIC_URL=https://app.korsik-demo.ru`; остальные строки `.env` сохранены, исходный resolved secret file скопирован в закрытый backup с правами 0600. Шесть app-сервисов перезапущены без сборки и проверены healthy; maintenance marker удалён. Профиль, retrieval и все image IDs сохранились. MAX API вернул ровно один webhook `https://app.korsik-demo.ru/hooks/max` с пятью ожидаемыми типами событий; удалена только прежняя подписка этой установки, сторонние подписки не затронуты. Проверка не отправляла MAX-сообщения: [ru-ingress-cutover-report.json](tests/ru-ingress-cutover-report.json).

Публичный HTTPS с Vast успешно вернул полный HTML с обычной CA/hostname-проверкой. С Mac последующие прямые попытки, включая явный IPv4 и обход proxy, завершились на TLS handshake до HTTP. Поэтому свежий внешний login/cookie flow сейчас не объявляется PASS. Переключение адреса не меняло nginx на Vast и не подтверждает сохранение исходного `X-Forwarded-Proto` на всех переходах.

## Восстановление и данные

Настроены heartbeat worker/scheduler и контроль живых фоновых задач MAX. Установлены ограниченный host watchdog и systemd units. `korsik-runtime.service` включён для следующего boot; в начальной проверке он **не запускался**. `korsik-watchdog.timer` включён и активен, backup timer сохранён. Два фактических прохода исправленного watchdog увидели все 14 сервисов в штатном состоянии и не перезапускали их. Эта проверка относится к начальному runtime-снимку; текущие healthy/image IDs подтверждены последующими web и cutover протоколами.

Изолированная проверка остановленного контейнера на этой VM подтвердила восстановление после startup grace и трёх наблюдений; maintenance marker запретил действие. Первая ошибка тестового harness и обнаруженная ошибка необязательного Docker Health сохранены в отчётах; Health исправлен, исправление проверено на реальном inventory. Рабочие контейнеры для fault injection не останавливались. Физическая перезагрузка VM не выполнялась, отказ провайдера этим механизмом не устраняется.

Перед установкой сохранены исходники, конфигурация, rollback tags и согласованный SQL/blob backup в закрытом каталоге `/opt/korsik/release18-before/`. Секреты в исходный архив не входят. Patch-архив финальных двух образов проверен загрузкой; cold restore именно этого patch-архива не выполнялся.
