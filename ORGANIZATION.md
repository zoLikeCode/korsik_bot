# Оргструктура

HR создаёт направления, отделы и команды, выбирает родительское подразделение и руководителя. В карточке существующего сотрудника назначаются подразделение и непосредственный руководитель. Пустое поле ручного руководителя означает наследование руководителя подразделения; для самого руководителя поиск продолжается в родительском подразделении. Карточка показывает цепочку руководителей и прямых подчинённых, каждый человек открывается по нажатию. Сотрудники без назначения остаются в отдельном списке.

## Хранение

Схема PostgreSQL не меняется. Подразделения — строки `domain_entities` с `kind=org_unit`; `parent_id` — родитель подразделения, `status=ACTIVE|ARCHIVED`. JSON `data` содержит `title`, `type=DIRECTION|DEPARTMENT|TEAM`, `head_employee_id`, `legal_entity_id`, `site_id`. В JSON существующего сотрудника добавляются `org_unit_id` и `reports_to_employee_id`. Версия строки используется для `ETag`/`If-Match`.

Старое поле `employee.data.manager_id` ссылается на **учётную запись User** и продолжает определять доступ менеджера и назначение задач. Новые связи дерева ссылаются на **Employee Entity**. Они не меняют роли, доступы, назначения сценариев или отправку сообщений. При отсутствии ручной связи и руководителя подразделения используется старый руководитель через `User.employee_id`, если такая привязка есть. Текстовое `department` сохраняется.

## API

| Метод | Путь после `/api/v1` | Назначение |
|---|---|---|
| GET | `/organization` | Доступные подразделения и безопасные карточки |
| POST | `/organization/units` | Создать подразделение |
| PATCH | `/organization/units/{id}` | Изменить или архивировать пустое подразделение |
| GET | `/organization/employees/{id}` | Карточка, `manager_chain`, `direct_reports` |
| PATCH | `/organization/employees/{id}` | Членство и ручной руководитель |
| GET | `/organization/employees/{id}/photo` | Авторизованная миниатюра фото |

PATCH требует актуальный `If-Match`; формы отправляют только изменённые поля. Так переименование сохраняет руководителя, скрытого областью доступа. При 412 доступна явная загрузка актуальной версии. Мутации сериализуются транзакционной advisory-блокировкой PostgreSQL; после неё строки перечитываются. Проверяются циклы подразделений и всей вычисляемой цепочки сотрудников, включая руководителей подразделений. Назначение самого себя, отсутствующего, завершившего найм или недоступного сотрудника и пересечение юрлиц отклоняются. Непустое подразделение архивировать нельзя. Интерфейс предоставляет создание и редактирование, архивирование доступно через API.

## Доступ и фото

HR_ADMIN и HR_SPECIALIST редактируют свою область. HEAD_TALENT и MANAGER читают доступную структуру. EMPLOYEE видит минимальный рабочий справочник действующих сотрудников своего юрлица. Для менеджера без собственной карточки область выводится из существующей команды и ограничений scope. PLATFORM_ADMIN не получает кадровый справочник. Недоступные руководители скрываются, цепочка обрывается на границе области.

Проекция содержит имя, должность/отдел, подразделение и связи. В ней нет кадровых заметок, ответов опросов, MAX ID, телефонов, личной почты и текста профиля. Справочник не расширяет доступ к HR-карточкам и диалогам.

Фото — валидированное изображение текущего периода найма. HR и сам сотрудник получают разрешённое фото; руководитель — только при действующем адресном согласовании публикации. Согласие на адресную публикацию не превращается в публикацию всему юрлицу. Остальным показываются инициалы. Endpoint повторно проверяет права, выдаёт JPEG до 256×256, убирает метаданные, использует `private, no-store`. Прямых публичных URL к blob-хранилищу нет.

При завершении найма сотрудник исчезает из справочника. Устаревшие ссылки на завершившего найм или переведённого в другое юрлицо сотрудника не раскрывают его карточку. HR может заменить связь, исторические данные сохраняются.

## Проверки

Тесты покрывают три уровня иерархии, наследование и явные связи, циклы, scope/юрлица/площадки, устаревший ETag, сохранение скрытых связей, архивирование, завершение найма, перевод и фото. В браузере локально проверены создание вложенных подразделений, назначение существующего сотрудника, повторное открытие и переходы по цепочке. Для тестового дерева используются только синтетические сотрудники; MAX и модели не вызываются.
