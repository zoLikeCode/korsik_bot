## Запуск

Требуются Docker Engine + Compose 2.24.4+, Linux x86-64; FULL использует NVIDIA
GPU с 12 ГБ памяти и рабочий NVIDIA Container Toolkit. CPU-модели фактически
проверены на AVX без AVX2. Для этой конфигурации рекомендуется 32–48 ГБ RAM.

1. `cp .env.example .env`; укажите путь к заранее подготовленным моделям и режим.
2. На Linux от root: `python3 scripts/init-secrets.py --directory ./secrets --owner 10001`,
   затем `chmod 644 ./secrets/db_bootstrap`. Родительский каталог остаётся 700.
3. Поместите токен MAX в `secrets/max_token`, права 600, владелец UID/GID10001.
   Секреты в git не входят.
4. На подключённом сборочном стенде подготовьте веса по pinned revisions:
   `python3 scripts/fetch-models.py --destination ./models` и
   `python3 services/model_server/fetch_parser_models.py --target ./models/docling`.
   Затем явно импортируйте ограниченный инженерный review выбранного 4B:
   `python3 scripts/install-quality-report.py --bundle ./models/generator-4b --report tests/model-quality/qwen-4b-release24.json`.
   Команда проверяет точное совпадение весов и pipeline; при отказе нужна новая оценка.
   Для изолированного контура перенесите готовые образы и каталоги моделей.
5. Соберите базовый parser:
   `docker build -t korsik-parser:local -f services/model_server/Dockerfile.parser .`.
   Затем `docker compose build` и `docker compose up -d --no-build`.
6. Первичная миграция и справочники создаются одноразовым `migrate`. Только на
   новой установке с пустой таблицей пользователей создаётся скрытый установочный
   аккаунт: логин `admin`, пароль `admin`, роль руководителя по подбору персонала.
   Сразу после входа необходимо сменить оба реквизита; до этого остальные API
   кабинета закрыты. Служебный аккаунт не отображается в списках сотрудников, HR
   и оргструктуре. Повторный bootstrap не создаёт аккаунт в существующей системе
   и не сбрасывает логины, пароли или роли. Параметры `ADMIN_EMAIL` и файл
   `secrets/admin_password` используются только операторскими legacy-скриптами;
   перед их запуском укажите собственный изменённый логин и пароль.

На Linux выдайте владельцу UID10001 право чтения app-секретов и файлов моделей.
Файл `db_bootstrap` также должен быть доступен процессу Postgres через secret
mount. На демонстрационном сервере секреты хранятся в закрытом каталоге хоста;
обычные контейнеры получают только свои отдельные файлы.

По умолчанию кабинет слушает `127.0.0.1:8080`, а демонстрационный HTTPS Quick
Tunnel автоматически регистрирует MAX webhook. Адрес Quick Tunnel меняется при
его пересоздании: актуальное значение в `docker compose exec tunnel cat
/run/tunnel/public_url`. Это временный транспорт стенда. В компании используется
собственный доверенный HTTPS:443: задайте `MAX_PUBLIC_URL` и запускайте профиль
[on-prem](deploy/compose.onprem.yaml), направив reverse proxy на web:8080.

## Первый рабочий маршрут

- HR создаёт сотрудника, указывает руководителя, даты и часовой пояс.
- HR выдаёт одноразовое приглашение. Сотрудник открывает его в MAX; действующее
  приглашение автоматически активирует привязку без второго подтверждения HR.
- Сотрудник получает приветствие, задаёт вопросы обычным текстом и кнопками,
  проходит точечные вопросы и анкеты. Свободный ввод анкеты требует отдельного
  подтверждения. До явного «Ответить» текст является вопросом ассистенту; при
  открытом вводе можно отменить его или выбрать «Это вопрос Корсику» у черновика.
- HR принимает обращение в кабинете и отвечает в тот же MAX-диалог; режим HUMAN
  приостанавливает автоматические сообщения до явного возврата боту.
- Руководитель видит свою команду и задачи. Личные HR-тексты ему не открываются.
  Уведомления о дашбордах включаются в настройках после собственной MAX-привязки.

Исходные 68 строк Excel, 28 ONB-групп и пять анкет встроены в начальную программу.
Не переданные компанией карты, картинки, контакты и персональные планы отмечены
в программе как требующие наполнения. Демонстрационная пятидневка явно помечена;
HR настраивает реальные сменные календари и даты перед корпоративным запуском.

## Документы и RAG

Три предоставленных PPTX находятся в `seed/examples/`. Через кабинет HR можно
создать документ, загрузить PDF/PPTX/изображение/текст, просмотреть страницы,
исправить OCR/таблицы, описать значимые изображения, проверить кандидатную базу
и опубликовать согласованную редакцию. Сам факт загрузки не делает источник
доступным сотруднику. Ошибка parser/index сохраняет действующую базу.

Parser использует PDFium + pdfplumber, локальный Tesseract rus/eng, нативный PPTX
и LibreOffice для предпросмотра; структурный профиль добавляет локальные
Docling Heron/TableFormer. Parser не получает пароль БД. Все веса и языки OCR
подготовлены заранее; контейнеры AI и данных подключены к внутренним сетям.

FULL: Granite97 multilingual r2 → dense+sparse Qdrant → Horizon reranker →
локальная Qwen3.5-4B на GPU. На имеющейся VM она прошла ограниченный
инженерный прогон с защитными правилами; 0.8B/2B показали смысловые ошибки
и не выбраны для этого развёртывания. Нормативные пункты и полные перечисления
могут возвращаться точной выдержкой, отсутствующие приложения запрашиваются у HR. Это решение не увеличивает тариф имеющейся VM.
Ответ содержит подтверждающие источники. Отозванный источник
перестаёт открываться, включая историю и отложенную доставку. При ошибке или
непроверенной генерации используется полная допустимая выдержка либо HR.
Отсутствие поддержки темы или явно названной системы в источниках, а также
явный отказ модели приводят к HR без нерелевантных выдержек и вложений.
Механические проверки чисел/ссылок не считаются доказательством качества модели.

В `/api/docs` доступны локальный HTML-каталог фактических маршрутов и полная схема:
он работает без JavaScript, внешних ресурсов и доступа к интернету. Машиночитаемый
контракт доступен по `/api/openapi.json`; внешние Swagger/ReDoc не подключаются.
[openapi.json](openapi.json)
генерируется из кода. Реестр локальных моделей показывает hashes и revisions;
профиль активируется после реального runtime smoke и освобождения очереди.
CORE — режим без генерации, с явным ограничением диалога, сценарии продолжаются.

## Проверки и эксплуатация

```sh
PYTHONPATH=backend python -m pytest
cd frontend && npm ci && npm test -- --run && npm run build
```

Тесты охватывают полный маршрут, календари, версионирование, анкеты, MAX retry,
проверки привязки, HR handoff, изоляцию документов, OCR review, публикацию,
авторизацию и session/CSRF/idempotency. Реальные проверки сервера и моделей
записываются отдельно от unit-тестов; синтетический sentiment fixture не
подтверждает качество на отзывах компании и требует HR review.

`docker compose ps`; `docker compose logs --tail 50 worker scheduler`.
Технические ошибки не содержат токены, пароли и полный текст переписки.
У MAX неопределённый результат отправки получает `UNKNOWN_DELIVERY`: повторная
рассылка вслепую отключена. Транспорт имеет отдельную SQL-роль без доступа к HR.

Резервирование: `scripts/backup.sh /secure/backup/path`.
Проверка восстановления: `scripts/check-restore.sh /secure/backup/path/<timestamp>`.
Проверка создаёт отдельную временную БД и не перезаписывает рабочую. БД и файлы
авторитетны; векторный индекс можно перестроить. Секреты сохраняются отдельно.
После восстановления БД и файлов запустить `docker compose run --rm --no-deps api python -m korsik.manage reindex`:
команда строит векторную проекцию только текущих опубликованных версий и проверяет
fingerprint энкодера и неизменность снимка. Исходные файлы и SQL при этом не удаляются.
Для подготовки образов изолированной поставки:
`scripts/export-offline-bundle.sh /secure/korsik-offline-bundle`. Каталог должен
находиться вне каталога приложения.
Скрипт создаёт архивы образов, закреплённых моделей с лицензиями и исходников,
SHA256-манифест и инструкцию установки. Секреты и рабочие данные в поставку не входят.

`scripts/check-offline-restore.sh <backup> <isolated-check-directory>` разворачивает
отдельный Compose project из копии БД и файлов, заново строит Qdrant, выполняет
локальные OCR/ответ/анализ/дашборд и проверяет работу HR при остановленном
генераторе. Использует вторую GPU (по умолчанию 0), отдельные секреты и volumes;
MAX и туннель не запускает. После проверки удаляет только свой временный project.

Airflow остаётся отдельной опцией исходного дизайна; текущий durable scheduler
реализует сроки, напоминания, дайджесты и повторы в PostgreSQL без Airflow.
Внешние AI API, внешние шрифты и CDN ресурсов интерфейса не используются.
